# CodeMind 教辅平台 · 异步任务设计

> 文档性质：异步任务基础设施的详细设计（任务队列引入方案）
> 更新时间：2026-10-15
> 配套文档：《后端落地问题清单.md》（2.8 节为本设计结论摘要）《API设计文档.md》（接口约定）《架构设计.md》

---

## 一、背景与问题

### 1.1 现状

全同步架构：WSGI + 同步 DRF 视图。一个请求从头到尾在一个 HTTP 连接内完成，没有任务队列、没有定时机制。

### 1.2 风险量化（为什么必须引入异步）

| 接口 | 慢点分析 | 后果 |
|---|---|---|
| `POST /api/import/` | `make_password` 是 CPU 密集操作（PBKDF2 约 60~100ms/次）。**导入 1 万学生仅密码哈希 ≈ 10~16 分钟**，另有 xlsx 解析 + 逐条落库 | 生产 Nginx 默认 60s 超时，请求必然中断；worker 被长期占死 |
| AI 批改（homework:ai，若保留） | LLM API 单次 10~60s | 同步必超时 |
| 作业提醒（homework:remind） | 邮件/短信串行发送，一个班几十次调用 | 几十秒起步 |
| 找回密码邮件 | SMTP 慢时 5~10s | 尚可容忍（单封） |

### 1.3 设计目标

1. 慢活移出 HTTP 请求：请求只负责"受理"，执行交给后台 worker
2. 前端可查询执行进度与结果（提交→轮询模式）
3. Windows 开发环境可用、部署零额外中间件（SQLite 时代就能跑）
4. 任务安全不缩水：权限、幂等、防滥用与原同步接口同级
5. 补上定时任务机制（作业截止提醒、清理类任务）

## 二、技术选型

| 方案 | 评估 | 结论 |
|---|---|---|
| Celery + Redis | 工业标准，但 **Windows 开发需特殊 pool**（solo/gevent）、Redis 无 Windows 官方版；引入 Redis 增加部署复杂度 | 暂缓 |
| **django-q2** | **Windows 完全兼容**；broker 用 Django ORM（SQLite/MySQL/PG 均可，零额外中间件）；内置 schedule 定时任务；支持超时/重试/结果存储 | **选定** |
| Huey | 轻量，但 broker 依赖 Redis 或文件，调度功能弱于 q2 | 不选 |
| 后台线程 | 进程重启丢任务、无重试 | 仅临时过渡 |

**迁移路径**：任务函数一律设计为**模块级纯函数**（参数只传 id/路径，不传对象、不依赖 request）。将来若部署 Linux+Redis 且规模扩大，可平滑迁移 Celery——函数签名不变，只换提交与运行入口（见附录对照表）。

## 三、总体架构

### 3.1 架构图

```
浏览器/前端
   │ ① POST /api/import/（multipart，仅受理）
   ▼
Django Web 进程（gunicorn/runserver）
   │ ② 同步预检：权限、文件格式、大小、行数上限
   │ ③ 文件落盘 MEDIA_ROOT/tmp/imports/
   │ ④ 建 AsyncTask 记录（status=pending）
   │ ⑤ async_task() 投递到队列 → 立即返回 {"taskId": n}
   ▼
django-q2 队列（Django ORM broker，就是数据库里一张队列表）
   ▼
qcluster worker 进程（独立于 Web 进程）
   │ ⑥ 取任务 → 执行纯函数（重新校验权限 → 逐行导入 → 更新 progress）
   │ ⑦ 结果写回 AsyncTask（done/failed + result/error）
   │ ⑧ 清理临时文件
   ▼
前端 ⑨ 每 2s 轮询 GET /api/tasks/<id>/ 直到终态，展示结果
```

### 3.2 新应用 `tasks` 的职责

| 文件 | 职责 |
|---|---|
| `models.py` | AsyncTask 统一任务表 |
| `api.py` + `api_urls.py` | `GET /api/tasks/`、`GET /api/tasks/<id>/` 查询接口 |
| `tasks_import.py` | 导入类任务函数（本轮落地） |
| `tasks_ai.py` / `tasks_remind.py` | AI 批改、提醒类任务函数（后续功能轮） |
| `schedules.py` | 定时任务注册（清理类） |
| `admin.py` | 任务表后台查看（超管排障） |
| `tests.py` | 模型/API/任务函数测试 |

业务逻辑本身仍在各业务应用（导入逻辑在 academics），tasks 只管"任务的生命周期"。

## 四、AsyncTask 模型设计

### 4.1 完整模型

```python
from django.conf import settings
from django.db import models


class AsyncTask(models.Model):
    """异步任务统一记录：提交→轮询模式的地基

    一次异步操作一条记录：提交时创建（pending），worker 执行时更新
    （running → done/failed），前端轮询本表获知进度与结果。
    """
    STATUS_PENDING = 'pending'
    STATUS_RUNNING = 'running'
    STATUS_DONE = 'done'
    STATUS_FAILED = 'failed'
    STATUS_CHOICES = [
        (STATUS_PENDING, '等待中'),
        (STATUS_RUNNING, '执行中'),
        (STATUS_DONE, '已完成'),
        (STATUS_FAILED, '失败'),
    ]

    TYPE_IMPORT = 'import'            # 批量导入（教务 xlsx / 题库 ZIP）
    TYPE_AI = 'ai_analyze'            # AI 批改分析（后续轮次）
    TYPE_REMIND = 'remind'            # 作业提醒（后续轮次）
    TYPE_CHOICES = [
        (TYPE_IMPORT, '批量导入'),
        (TYPE_AI, 'AI批改'),
        (TYPE_REMIND, '作业提醒'),
    ]

    type = models.CharField('任务类型', max_length=20, choices=TYPE_CHOICES)
    status = models.CharField('状态', max_length=10, choices=STATUS_CHOICES,
                              default=STATUS_PENDING)
    total = models.PositiveIntegerField('总量', default=0)   # 总行数等（预检时算好，供进度计算）
    progress = models.PositiveIntegerField('进度', default=0)  # 0-100
    result = models.JSONField('结果', null=True, blank=True)  # 成功结果（successCount/errors）
    error = models.TextField('错误信息', blank=True)          # 失败原因（已脱敏，前端可见）
    created_by = models.ForeignKey(settings.AUTH_USER_MODEL, models.CASCADE,
                                   verbose_name='提交人',
                                   related_name='async_tasks')
    created_at = models.DateTimeField('提交时间', auto_now_add=True)
    started_at = models.DateTimeField('开始时间', null=True, blank=True)
    finished_at = models.DateTimeField('结束时间', null=True, blank=True)

    class Meta:
        verbose_name = '异步任务'
        verbose_name_plural = '异步任务'
        ordering = ['-created_at']
        indexes = [
            # 高频查询：某用户的近期任务、排队中的任务（限流检查用）
            models.Index(fields=['created_by', 'created_at']),
            models.Index(fields=['status']),
        ]

    def __str__(self):
        return f'{self.get_type_display()} #{self.pk}（{self.get_status_display()}）'
```

### 4.2 字段说明要点

| 字段 | 设计意图 |
|---|---|
| `total` | 预检阶段统计（导入=数据总行数），worker 才能算百分比：`progress = 已处理 * 100 / total` |
| `result` JSON | 与现有导入响应 `{"successCount": n, "errors": [...]}` 结构一致，前端逻辑可复用 |
| `error` | **只存脱敏后的信息**（如"第 12 行：学号格式错误"），未知异常存"任务执行异常，请联系管理员"，完整堆栈进日志 |
| `created_by` | 任务归属：查询接口按它过滤（对象级防探测）；worker 内靠它重新加载用户做权限校验 |

### 4.3 状态机

```
pending ──worker 领取──→ running ──成功──→ done（写 result）
   │                       │
   │                       └──异常──→ failed（写 error，重试时回到 pending）
   │
   └──队列重启/投递失败重试──→ 重新 pending（max_attempts=2，见第五章）
```

终态（done/failed）后不再变更；`started_at`/`finished_at` 供排障与"任务卡死"判断（运行超过 timeout 视为异常）。

## 五、Q_CLUSTER 配置（settings.py 新增段）

```python
# ==================== 异步任务队列（django-q2）====================
# worker 独立进程运行：python manage.py qcluster
# broker 用 Django ORM（django_q_ormq 表），无需 Redis 等中间件
Q_CLUSTER = {
    'name': 'codemind',        # 集群名（多环境部署区分用）
    'workers': 2,              # worker 进程数：开发 1，生产 2~4（按 CPU 核数）
    'timeout': 600,            # 单任务超时（秒）：导入类任务给足 10 分钟
    'retry': 700,              # 失败重试等待（秒）：必须大于 timeout（django-q2 官方约束，
                               # 否则任务超时被杀前就重投，同一任务并发执行）
    'max_attempts': 2,         # 最大尝试次数（含首次）——要求任务函数幂等
    'queue_limit': 50,         # 队列积压上限，防恶意提交撑爆内存
    'orm': 'default',          # 关键：用 Django ORM 做 broker
    'poll': 0.5,               # worker 拉取任务的轮询间隔（秒）
    'save_limit': 250,         # ORM 中保留的队列执行记录条数
    'catch_up': False,         # worker 停机期间的定时任务不补跑
    'ack_failures': True,      # 失败任务确认掉，避免卡队列
}
```

| 参数 | 调优说明 |
|---|---|
| `timeout=600` | 统一给 10 分钟；AI 类快任务提交时单独覆盖（`async_task(..., timeout=150)`） |
| `max_attempts=2` | 重试依赖任务幂等（见 8.3），导入任务按编号查重跳过，天然安全 |
| `queue_limit=50` | 配合 8.6 的用户级限流（每人同时 pending/running ≤ 3）双重防滥用 |

## 六、任务函数设计

### 6.1 通用模式（每个异步任务一个纯函数的模板）

```python
# tasks/tasks_import.py（示意模板，实际按业务拆分文件）
import logging
from django.utils import timezone
from tasks.models import AsyncTask
from users.models import User

logger = logging.getLogger('codemind.tasks')


def runImportTask(taskId, filePath, importType, userId):
    """批量导入任务：worker 进程内执行，不依赖 request"""
    task = AsyncTask.objects.get(pk=taskId)
    task.status = AsyncTask.STATUS_RUNNING
    task.started_at = timezone.now()
    task.save()

    def reportProgress(doneCount):
        """进度回调：按 1% 粒度写库，避免每行都写数据库"""
        percent = int(doneCount * 100 / task.total) if task.total else 100
        if percent != task.progress:
            task.progress = percent
            task.save(update_fields=['progress'])

    try:
        # ① 权限延续：任务内重新加载用户校验，不信任任务参数
        user = User.objects.get(pk=userId)
        if not user.has_perm(...):            # 按导入类型查对应权限码
            raise PermissionError('无导入权限')

        # ② 复用 academics 抽出的纯函数（幂等：编号查重跳过），带进度回调
        successCount, errors = importStudentsFromFile(filePath, reportProgress)

        task.status = AsyncTask.STATUS_DONE
        task.progress = 100
        task.result = {'successCount': successCount, 'errors': errors}
    except Exception as e:
        # ③ 错误脱敏：已知业务错误原样存，未知异常只存通用提示 + 完整堆栈进日志
        logger.exception('异步任务 %s 失败', taskId)
        task.status = AsyncTask.STATUS_FAILED
        task.error = getattr(e, 'message', '任务执行异常，请联系管理员')
    finally:
        task.finished_at = timezone.now()
        task.save()
        # ④ 清理临时文件（孤儿文件由定时任务兜底，见第九章）
        if os.path.exists(filePath):
            os.remove(filePath)
```

### 6.2 导入任务（本轮落地）

| 项 | 设计 |
|---|---|
| 任务类型 | `import` 一个类型覆盖三种导入，`importType` 参数区分 student/teacher/course |
| 前置重构 | academics 现有导入逻辑从视图抽成纯函数：`importStudentsFromFile(file, onProgress=None)`、`importTeachersFromFile(...)`、`importCoursesFromFile(...)`，返回 `(successCount, errors)`；同步路径保留（作为降级与测试用） |
| progress 计算 | `total` = 预检时统计的数据行数；每处理 1% 写库一次 |
| result 结构 | `{"successCount": n, "errors": [{"line": 2, "reason": "..."}]}` —— 与现有同步响应完全一致 |
| 权限 | 任务内按 importType 重查：student/teacher 需 `class:manage`，course 需 `course:manage` |
| 幂等 | 按 username（学生/教师）/ code（课程）查重跳过——与现有导入行为一致，重试安全 |

> **2026-10-20 补充（题库 ZIP 导入）**：题库批量导入目前为**同步执行**
> （约 1000 题实测秒级），仅复用 `AsyncTask(type=import)` 记录导入历史、
> 结果与错误明细，不投递 q2 worker；管理页直接读取该记录展示最近批次。
> 若未来单批规模显著增大或出现超时，可按本章模式改为异步任务，
> 复用 `teaching/problem_import.py` 的解析与落库逻辑作为 worker 任务主体。

### 6.3 AI 批改任务（后续轮次，接口预留）

- 提交：`async_task('tasks.tasks_ai.runAiAnalyze', taskId, homeworkId, studentId, userId, timeout=150)`（LLM 慢，单独超时）
- 任务内：重查 `homework:ai` 权限 + `getTeacherTeachingClass` 对象级校验（teachingClassId 从 homework 反查，不信任参数）
- 失败重试：LLM 波动重试一次（max_attempts=2 足够）

### 6.4 提醒任务（后续轮次，接口预留）

- 单班提醒可先同步（站内信批量 insert 快）；**邮件/短信必须异步**
- 任务内同样走权限延续 + 对象级校验

## 七、API 设计

### 7.1 `POST /api/import/` 改造（提交→受理）

**请求**：与现在完全一致（multipart：`type` + `file`），前端只需改响应处理。

**同步预检（400 快速失败，不排队）**：
1. 登录 + 权限码（class:manage / course:manage，不变）
2. 文件存在、xlsx 可解析、表头合法
3. 文件大小 ≤ 5MB、数据行数 ≤ 5000（一期上限，超限提示分批导入）
4. 统计总行数 → 存入 `AsyncTask.total`

**受理流程**：
```
预检通过 → 文件保存到 MEDIA_ROOT/tmp/imports/YYYYMMDD/<uuid>.xlsx
        → 创建 AsyncTask（pending, total=行数）
        → async_task('tasks.tasks_import.runImportTask', taskId, filePath, importType, userId)
        → 200 {"taskId": 12, "status": "pending"}
```

> 一期上限 5000 行的依据：5000 次密码哈希 ≈ 5~8 分钟，在 timeout=600s 内；万级数据等生产库（MySQL）+ 调参后再放开。

### 7.2 `GET /api/tasks/` — 我的任务列表

- 权限：登录即可（IsAuthenticated）；**仅返回 created_by = 自己的任务**，超管可见全部
- 分页：每页 20，按 created_at 倒序

```json
{
  "count": 3,
  "results": [
    {"id": 12, "type": "import", "status": "done", "progress": 100,
     "total": 200, "createdAt": "2026-10-15 10:00", "finishedAt": "2026-10-15 10:03"}
  ]
}
```

### 7.3 `GET /api/tasks/<taskId>/` — 任务详情（轮询目标）

- **对象级校验**：`task.created_by == request.user`，否则 **404**（防探测，与项目 404 语义一致）；超管放行

```json
{"id": 12, "type": "import", "status": "running", "progress": 40,
 "total": 200, "result": null, "error": null}
{"id": 12, "type": "import", "status": "done", "progress": 100,
 "result": {"successCount": 198, "errors": [{"line": 15, "reason": "学号格式错误"}]}}
{"id": 12, "type": "import", "status": "failed", "progress": 0,
 "error": "任务执行异常，请联系管理员"}
```

### 7.4 前端轮询协议

| 项 | 约定 |
|---|---|
| 基础间隔 | 2s |
| 退避 | 连续 5 次 status/progress 无变化 → 间隔增至 5s |
| 停止条件 | 终态（done/failed）；页面卸载停止轮询 |
| 异常兜底 | 超过 30 分钟未终态 → 提示"任务执行超时，请在任务列表中查看"（任务侧 timeout=600s，正常不会触发） |

## 八、安全设计

| # | 风险 | 对策 |
|---|---|---|
| 8.1 | **权限在异步中丢失**（任务里没有 request.session） | 任务参数只传 `userId`，worker 内重新加载用户、重查功能权限码 + 对象级校验（clazzId 等从业务对象反查，**不信任任务参数**） |
| 8.2 | 任务参数被篡改/注入 | 参数只允许 id/路径/枚举（importType 白名单校验）；文件路径由服务端生成（uuid 文件名），不接受客户端路径 |
| 8.3 | 重试导致重复数据 | 任务函数幂等：导入按 username/code 查重跳过（现有逻辑）；重试只补未完成部分 |
| 8.4 | 临时文件泄露/残留 | 文件放 `MEDIA_ROOT/tmp/`（与业务媒体隔离、不入静态服务）；任务终态即删；定时任务兜底清孤儿 |
| 8.5 | 错误信息泄露内部结构 | `task.error` 只存脱敏文案；堆栈只进服务端日志（LOGGING 配套） |
| 8.6 | 恶意批量提交打爆队列 | 用户级限流：同一用户 pending/running 任务 > 3 个 → 新提交 400；配合 `queue_limit=50` |

## 九、定时任务设计（django-q2 schedule）

| 任务 | 周期 | 说明 |
|---|---|---|
| 过期会话清理 | 每日 3:00 | `schedule('django.core.management.call_command', 'clearsessions', schedule_type=Schedule.CRON, cron='0 3 * * *')` |
| 临时文件孤儿清理 | 每日 4:00 | 扫 `MEDIA_ROOT/tmp/` 删除 mtime 超 24h 的文件 |
| 作业截止提醒（若做） | 每小时 | 扫 deadline 在 (now, now+24h] 且未提醒的作业 → 站内信/邮件（依赖 Homework 模型，后续轮次加） |

注册位置：`tasks/schedules.py`，首次部署时执行一次注册函数即可（幂等注册）。

## 十、部署设计

## 十一、测试设计

| 层 | 用例 |
|---|---|
| 模型 | 状态默认值、索引存在、str 输出 |
| API 越权矩阵 | 未登录 403；用户 A 查用户 B 的任务 → 404；超管可见全部；pending/running > 3 再提交 → 400 |
| 任务函数单测 | **直接同步调用**任务函数（不走队列）：断言 done 后 result 结构与同步导入一致、failed 后 error 脱敏、临时文件被清理 |
| 幂等 | 同一文件执行两次任务：第二次 successCount=0（全部查重跳过），不产生重复账号 |
| 队列集成 | 测试环境 `Q_CLUSTER['sync'] = True`（async_task 同步执行），跑通"提交→轮询→终态"全链路 |

> 注意：qcluster 依赖的 django_q 表需要 migrate；CI/测试用 sync=True 避免起 worker 进程。

## 十三、附录：与 Celery 的迁移对照

| 维度 | django-q2（当前） | Celery（未来可选） |
|---|---|---|
| 提交 | `async_task('tasks.tasks_import.runImportTask', taskId, filePath, importType, userId)` | `runImportTask.delay(taskId, filePath, importType, userId)` |
| worker | `manage.py qcluster` | `celery -A codemind worker` |
| 定时 | django-q2 Schedule | celery beat |
| broker | Django ORM | Redis/RabbitMQ |
| 任务函数 | **完全不变**（模块级纯函数，签名一致） | 同左 |

任务函数与 AsyncTask 表是自有的、与队列框架解耦——迁移只换"投递与运行"两端，业务零改动。
