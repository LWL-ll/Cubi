## 一、项目是干什么的

**CodeMind 是一个教辅平台**：教务管理课程与班级、教师给班级发通知/布置作业/批改、学生看作业/提交作业/看自己的学情画像。

技术栈：Django 6.1.2（后端框架）+ DRF（REST API）+ django-axes（防暴力破解）+ openpyxl（xlsx 导入）+ SQLite（数据库，生产计划换 MySQL）。

架构定位：**前后端分离**。主线是后端 API + 权限体系；`templates/` 里的页面只是开发预览，真正的前端以后单独做。

## 二、目录总览（带注释的目录树）

```
codemind/                    ← 项目根目录
├── manage.py                ← Django 命令入口（runserver / migrate / test 都从这进）
├── db.sqlite3               ← 数据库文件（所有数据都在这里）
│
├── codemind/                ← 项目配置包（整个项目的"总开关"，与项目同名）
│   ├── settings.py          ← 全局配置：应用注册、数据库、安全加固、axes 配置
│   ├── urls.py              ← 总路由表：所有 URL 从这里分发到各应用
│   ├── wsgi.py / asgi.py    ← 部署入口（服务器启动项目时从这里加载）
│   └── __init__.py          ← 包标记文件
│
├── users/                   ← 用户与权限（安全核心，四角色账号都在这）
├── academics/               ← 教务业务（课程→学院→班级三层、批量导入）
├── teaching/                ← 教学业务（教师工作台、学生工作台、对象级校验工具）
│
├── templates/               ← 页面模板（开发预览用，分 users/office/teaching 三组）
├── docs/                    ← 设计文档（本文件也在里面）
├── .idea/                   ← PyCharm 编辑器的配置（与项目运行无关）
└── .claude/                 ← Claude Code 的配置（审查技能等）
```

三个应用的分工一句话：

| 应用 | 一句话职责 |
|---|---|
| `users` | 谁来用（登录、角色、权限码）——"有没有资格" |
| `academics` | 教务管什么（课程、学院、班级、导入）——"组织架构" |
| `teaching` | 教学干什么（通知、作业、资料、画像）——"日常业务" |

## 三、逐文件夹讲解

### 3.1 codemind/ —— 项目配置包（总开关）

| 文件 | 作用 | 关键内容 |
|---|---|---|
| `settings.py` | **整个项目的全局配置**，改任何"全局行为"都在这 | `INSTALLED_APPS`（注册 5 个应用+DRF）、自定义 User 模型、axes 认证后端、登录锁定规则（失败5次锁1小时）、会话安全（Cookie HttpOnly、2小时过期）、数据库（SQLite）、中文时区 |
| `urls.py` | **总路由表**：URL 前缀分发到各应用 | 7 条挂载：`/admin/`、`/`→users、`/office/`→academics、`/teacher/`→teaching、`/student/`→teaching、`/api/`→academics、`/api/teacher/`→teaching |
| `wsgi.py` | 生产部署入口（服务器软件如 gunicorn 从这里加载项目） | 一般不用动 |
| `asgi.py` | 异步部署入口（预留，当前全同步架构用不上） | 一般不用动 |
| `__init__.py` | 空文件，标记这是一个 Python 包 | 不动 |

### 3.2 users/ —— 用户与权限（安全核心）

这个应用回答**"你是谁、你能干什么"**，是全项目安全防线。

| 文件 | 作用 | 关键内容 |
|---|---|---|
| `models.py` | **自定义用户模型** | 继承 Django 自带 User 并加 `name` 真实姓名字段；**23 个权限点注册在 `Meta.permissions`**（notice:manage、homework:publish……），四角色不分表、用 Group 区分 |
| `permissions.py` | **权限工具箱**（全项目共用的权限工具） | `hasPerm`（功能级校验）、`getGroupKey`（识别角色：教务/课程组/教师/学生）、`requirePerm`（页面装饰器）、`PermRequired`（API 权限类，视图声明 permCode 即自动校验）、`IsTeacherGroup`（教师接口入口校验） |
| `checks.py` | **权限一致性自动检查** | `manage.py check` 时自动比对：模型注册的权限 ↔ 权限码表 ↔ 分组分配 ↔ 数据库实际数据，四处不一致就报错——改权限后跑一遍防漏 |
| `tests.py` | **权限测试矩阵** | 10+ 用例，四角色 × 各端点边界全覆盖，改权限后必跑 |
| `api.py` | 认证 API | 登录 / 登出 / `me`（前端登录后调它拿权限码列表渲染界面） |
| `views.py` | 页面视图 | 登录页、登出（仅 POST 防 CSRF 强制登出）、首页（按分组显示工作台入口+权限总览） |
| `urls.py` | 路由 | 页面路由 + `/api/auth/` 三个接口 |
| `admin.py` | admin 后台注册 | 教务账号由管理员在 `/admin/` 添加并勾选分组 |
| `apps.py` | 应用配置 | 应用启动配置 |
| `migrations/` | 数据库迁移 | 0001 初始建表；**0003~0009 是权限分配迁移**（清空教师组→注册权限→分配教师/课程组/学生权限） |
| `static/` | 静态资源 | 登录页等页面用的 CSS/图片 |

### 3.3 academics/ —— 教务业务（组织架构）

这个应用回答**"学校有哪些课程、学院、班级，人怎么进班"**。

| 文件 | 作用 | 关键内容 |
|---|---|---|
| `models.py` | **教务数据模型（四张核心表）** | `Course`（课程）、`College`（学院）、`Clazz`（班级：students/teachers 两个 M2M）、`CourseCollege`（课程×学院：组长+教师池+班级，带属性的中间表）——课程→学院→班级三层结构的全部家当 |
| `student_no.py` | **学号规则**（单独抽出来就为这事） | 8 位学号解析：前4位年级、中2位学院代码、后2位班级序号。**正式格式定稿后只改这一个文件** |
| `api.py` | **教务 API**（前后端分离的主线） | 学院列表、课程 CRUD+开设学院、课程×学院设置（组长/教师池/班级/导入）、班级 CRUD+分配教师、通用批量导入 |
| `api_urls.py` | API 路由 | 挂 `/api/` 前缀 |
| `serializers.py` | DRF 序列化器 | 模型 ↔ JSON 的转换规则（列表返回哪些字段） |
| `urls.py` | 教务页面路由 | 挂 `/office/`：导入页、课程列表/详情、课程×学院页、班级详情（**路径必须从课程→学院→班级进入**） |
| `views.py` | 教务页面视图 | 每个页面视图都套 `requirePerm`（导入=class:manage、课程=course:manage……） |
| `tests.py` | 教务测试 | 三层结构、导入逻辑的测试 |
| `admin.py` / `apps.py` | 后台注册 / 应用配置 | |
| `migrations/` | 数据库迁移 | 含 0002-0004 三层结构重构迁移（旧 Course.clazzes 数据迁移到新表） |

### 3.4 teaching/ —— 教学业务（日常功能）

这个应用回答**"教师和学生每天干什么"**。模型还是空壳，但**安全工具已备好**。

| 文件 | 作用 | 关键内容 |
|---|---|---|

## 四、一次请求的旅程（文件是怎么协作的）

### 例 1：教务打开课程列表页

```
浏览器访问 /office/courses/
  → codemind/urls.py         匹配 office/ 前缀，转给 academics.urls
  → academics/urls.py         匹配 courses/，调用 views.renderCourseList
  → academics/views.py        @requirePerm('course:manage') 先查权限（users/permissions.py 的 hasPerm）
  → templates/office/course_list.html   渲染页面返回
  → 页面里的 JS 再调 GET /api/courses/
  → codemind/urls.py         匹配 api/ 前缀，转给 academics.api_urls
  → academics/api.py         视图声明 permCode，DRF 全局配置里的 PermRequired 自动校验
  → academics/serializers.py 把 Course 模型转成 JSON
  → 返回 JSON，前端渲染列表
```

要点：**页面路由和 API 路由是两条平行线**，页面负责"给 HTML"，API 负责"给 JSON"，都各自校验权限（后端防线）。

### 例 2：教师打开自己班级的详情

```
浏览器访问 /teacher/clazzes/1/
  → teaching/urls.py          → views.renderTeacherClazzDetail
  → teaching/helpers.py       requireTeacherGroup：必须是教师组（否则 403）
                              getTeacherClazz：clazz.teachers 含当前用户吗？不含 → 404
  → 通过则渲染 templates/teaching/clazz_detail.html（5 个 Tab 按权限码显隐）
```

要点：`teaching/helpers.py` 的 `getTeacherClazz` 是**对象级校验**——就算你是教师，不是这个班的教师也 404。后续通知、作业、资料接口全部要套它。

## 七、三条最重要的设计主线（看懂项目就这三条）

1. **权限防线两道**：功能级（users/permissions.py 的权限码）+ 对象级（teaching/helpers.py 的班级归属）。前端隐藏菜单只是体验，后端校验才是防线。
2. **课程→学院→班级三层结构**：所有教学数据挂班级（Clazz 是容器），教师/学生都挂班级上——对象级校验查的就是 `clazz.teachers` / `clazz.students`。
3. **前后端分离**：API 是主线（`/api/` 系列），templates 里的页面只是开发预览，将来前端独立开发，只调 API。
