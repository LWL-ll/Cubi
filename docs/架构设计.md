## 三、数据库设计

### 3.1 ER 图

```
users_user（平台账号）                       academics_course（课程）
   │ identities                              │ course
   ▼                                         ▼
users_schoolidentity（学工号绑定）      academics_courscollege（课程×学院）
   ├─ student_profile ──┐                    │ courseCollege（PROTECT）
   └─ teacher_profile   │                    ▼
             │          ▼          academics_teachingclass（教学班）
             ▼                       ├─ adminClasses（组成行政班 1~N）
users_studentprofile（学籍）          └─ teachers（授课教师）
   │ memberships            ▲
   ▼                        │
academics_classmembership   │
   │ admin_class            │ department
   ▼                        │
academics_adminclass（行政班）  academics_department（学院）
   │ major                        ▲
   ▼                              │ department
academics_major（专业）──department──┘

实线箭头 = ForeignKey / OneToOne；虚线 = ManyToMany（Django 自动建中间表）
```

### 3.2 逐表设计

**`users_user` — 用户表（平台账号，四角色共用一张）**

| 字段 | 类型 | 说明 |
|---|---|---|
| username | CharField(150) unique | 登录账号：封闭式下学生存学号、教师/教务存工号，唯一约束防撞号 |
| password | CharField | 哈希存储，永不明文 |
| name | CharField(50) | 真实姓名（业务显示用） |
| is_superuser / is_staff / is_active | Boolean | Django 自带开关 |
| last_login / date_joined | DateTime | 自带审计字段 |

角色没有 `role` 字段——角色用 Django 原生 Group（多对多）：一个用户可同属多组（课程组组长同时也是教师），权限在 admin 后台可勾选调整。

**身份与资料表（V2 新增，详见《数据库表重构设计.md》）**

- `users_schoolidentity`：学号/工号绑定（school_code、school_number、identity_type、verification_status），封闭式下导入即 verified，为将来接入 NSU 教务数据留口子
- `users_studentprofile`：学籍属性（major、enrollment_year、academic_status）
- `users_teacherprofile`：教职档案（department、title）——课程权限由任课关系决定，与所属学院无关

**`academics_department` — 学院（原 College 升级，V2）**

```
code = CharField(32, unique=True)   # 学院业务编码（新增）
name = CharField(100)
is_active = Bool                     # 是否启用（新增）
```

**`academics_major` — 专业（V2 新增层）**

```
department = FK(Department, PROTECT)   # 所属学院
code = CharField(32)                   # 专业编码
name / is_active
# unique_together = (department, code)
```

**`academics_adminclass` — 行政班级（原 Clazz 重构，V2）**

```
name            = CharField(50)      # 班级名（如"计科2301"）
major           = FK(Major, PROTECT) # 所属专业（原挂学院改挂专业）
enrollment_year = SmallInt           # 年级/入学年份（新增）
code            = CharField(32)      # 班级编码（可选）
# unique_together = (major, enrollment_year, name)
```

- 学生与教师**不再直接挂行政班**：学生关系走 ClassMembership（转班留痕）、教师任课挂教学班
- `on_delete=PROTECT`：有行政班的专业删不掉，防误删历史数据
- 业务约束：一个学生同一时间只属于一个行政班（服务层校验，换 MySQL 后补部分唯一索引）

**`academics_classmembership` — 学生-行政班关系（V2 新增）**

```
student_profile = FK(StudentProfile, CASCADE)
admin_class     = FK(AdminClass, CASCADE)
joined_at = DateField()          # 入班日期
left_at   = DateField(null)      # 离班日期；NULL = 当前在班
```

**`academics_course` — 课程**

```
code = CharField(20, unique=True)        # 课程编号（规则待定稿）
name = CharField(50)
colleges = M2M(College, through='CourseCollege')
```

**`academics_courscollege` — 课程×学院（三层结构的关键设计）**

```
course       = FK(Course, CASCADE)        # 课程删了，关联记录跟着删
department   = FK(Department, CASCADE)
leader       = FK(User, SET_NULL, null=True)  # 课程组组长
teachers     = M2M(User)                  # 本课程教师池
adminClasses = M2M(AdminClass)            # 本课程×学院可组教学班的行政班候选池
unique_together = (course, department)    # 同一课程×学院仅一条
```

**为什么要有这张表？** 课程和学院之间不只是"开没开设"，还带着三个属性：组长是谁、教师池有谁、有哪些班级。纯多对多存不了属性，所以用 `through` 显式建中间表，把属性挂在关系本身上——"带属性的多对多"。

`on_delete` 策略即业务规则：

| 删除对象 | 策略 | 意图 |
|---|---|---|
| 删课程/学院 | CASCADE | 关联记录无意义，一起删 |
| 删组长账号 | SET_NULL | 关联记录保留，组长置空（换人再指定） |
| 删学院（有班级） | PROTECT | 拒绝删除，保护历史数据 |

**`academics_teachingclass` — 教学班（授课单位，2026-10-18 设计定稿，详见《教学班级设计.md》）**

```
name          = CharField(50)        # 教学班名（如"计科2301-2302合班"）
term          = CharField(20)        # 学期（如"2026-2027-1"）
courseCollege = FK(CourseCollege, PROTECT)   # 归属课程×学院（天然锁学院，不可跨学院合班）
adminClasses  = M2M(AdminClass)      # 组成行政班（1~N 个，原子单位不拆分）
teachers      = M2M(User)            # 授课教师（须来自课程×学院教师池）
```

- 行政班是学籍概念、教学班是授课概念：**学生挂行政班，教师/通知/作业/资料挂教学班**
- 学生不直接挂教学班，归属由"学生→行政班→教学班"推导，无同步一致性问题
- 对象级校验：教师查 `teachingClass.teachers`、学生经行政班两跳推导

```

M2M 在数据库里就是一张只含两个外键的中间表，Django 自动建表自动查。

### 3.4 设计要点

1. **账号与身份分离**：User 管登录，SchoolIdentity 管学工号绑定，资料表管学籍/教职属性——四角色一张 User 表不变，角色 = Group，可多组共存
2. **教学班是教学数据的容器**：教师/通知/作业/资料挂教学班 → 对象级校验的锚点；行政班是学籍容器
3. **课程×学院用带属性的中间表**，承载组长/教师池/行政班候选池三层信息
4. **on_delete 即业务规则**：PROTECT 防误删、SET_NULL 保关联、CASCADE 随主删
5. **待建**：teaching/models.py 的作业/提交/通知/资料/题库——将全部外键到 TeachingClass（教学班）上，沿用"授课单位为容器"的思路
6. **行政班 vs 教学班**：教务导入的是行政班（学号解析决定，memberships 记录在班历史）；教学班按学期由 1~N 个行政班组成（详见《教学班级设计.md》）
7. **组织结构三层**：学院 → 专业 → 行政班（V2 新增专业层，见《数据库表重构设计.md》）

```

│           └─ 通用 profile:edit（四组都有）
├── 工具
│     ├── 功能级：hasPerm · getGroupKey

│     ├── API：PermRequired · IsTeacherGroup

## 五、请求校验流程（两级权限模型）

```
收到请求
  │
  ▼
① 登录了？ ───────否──────→ 页面 302 跳登录 / API 401
  │ 是
  ▼
② 分组入口校验（是不是教师组/学生组？）──否──→ 403
  │ 是
  ▼
③ 权限码校验 hasPerm（有没有这个功能？）──否──→ 403
  │ 是
  ▼
④ 对象级校验（这个班级我教/我在吗？）────否──→ 404（不暴露对象存在性）
  │ 是
  ▼
⑤ 执行业务逻辑
```

| 层级 | 载体 | 示例 |
|---|---|---|
| 功能级 | 分组权限码 | 教师有 `notice:manage` → 能用通知功能 |
| 对象级 | 业务接口内校验 | `teachingClass.teachers` 含当前教师 → 能对这个教学班发通知 |

①② = 页面装饰器；②③ = API 权限类；④ = getTeacherTeachingClass / getStudentTeachingClass。
第 ④ 层是防越权的关键：只查"能不能用"不够，还要查"能不能对这个对象用"。404 而非 403 是刻意设计：不暴露对象是否存在。

## 八、安全机制

1. **服务端强制校验**：前端隐藏菜单只影响体验，后端才是防线（页面装饰器 + API 权限类双轨）
2. **对象级校验**：教师→执教班级、学生→所在班级、教务→课程×学院上下文，越界一律 404
3. **防暴力破解**：django-axes 连续失败 5 次锁定 1 小时
4. **登出仅 POST**：防 CSRF 强制登出
5. **权限一致性检查**（users/checks.py）+ **权限测试矩阵**（users/tests.py），改权限必跑

## 九、业务规则

- 教师权限边界 = 其授课教学班集合（含个人题库）；学生权限边界 = 所在行政班推导出的教学班集合
- 无法删除已截止作业（待作业模型落地时实现）
- 教务账号仅管理员在 /admin/ 添加；教师/学生 xlsx 导入自动入组
- 课程组组长由教务设置，自动入组/移出
- 班级详情必须从课程×学院入口进入（跨课程 404）
