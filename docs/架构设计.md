## 三、数据库设计

### 3.1 ER 图

```
users_user（User）
   │
   │◄── teachers（执教）──┐
   │◄── students（在读）──┤
   │                      │
   │   academics_clazz（班级）◄──┐
   │        │ college（所属学院）  │ clazzes（课程班级）
   │        ▼                     │
   │   academics_college（学院）   │
   │        ▲                     │
   │        │ college             │
   │   academics_courscollege（课程×学院）
   │        ▲
   │        │ course
   │   academics_course（课程）

实线箭头 = ForeignKey；虚线 = ManyToMany（Django 自动建中间表）
```

### 3.2 逐表设计

**`users_user` — 用户表（四角色共用一张）**

| 字段 | 类型 | 说明 |
|---|---|---|
| username | CharField(150) unique | 登录账号：学生存学号、教师/教务存工号，唯一约束防撞号 |
| password | CharField | 哈希存储，永不明文 |
| name | CharField(50) | 真实姓名（业务显示用） |
| is_superuser / is_staff / is_active | Boolean | Django 自带开关 |
| last_login / date_joined | DateTime | 自带审计字段 |

角色没有 `role` 字段——角色用 Django 原生 Group（多对多）：一个用户可同属多组（课程组组长同时也是教师），权限在 admin 后台可勾选调整。

**`academics_college` — 学院**

```
name = CharField(50, unique=True)
```

学院没有导入入口：学生学号里解析出学院代码时自动 `get_or_create`，是三层结构里最稳定的一层。

**`academics_clazz` — 班级（承上启下的核心表）**

```
name     = CharField(50, unique=True)
college  = FK(College, null=True, on_delete=PROTECT)
students = M2M(User)      # 班级学生
teachers = M2M(User)      # 班级教师
```

- **教师和学生都挂在班级上**：所有教学功能（作业、通知、画像）都以班级为容器，对象级校验查的就是 `clazz.teachers` / `clazz.students` 含不含当前用户
- `on_delete=PROTECT`：有班级的学院删不掉，防误删历史数据
- 业务约束：一个学生只属于一个班级（导入时按学号强制），一个教师可执教多个班

**`academics_course` — 课程**

```
code = CharField(20, unique=True)        # 课程编号（规则待定稿）
name = CharField(50)
colleges = M2M(College, through='CourseCollege')
```

**`academics_courscollege` — 课程×学院（三层结构的关键设计）**

```
course   = FK(Course,  CASCADE)           # 课程删了，关联记录跟着删
college  = FK(College, CASCADE)
leader   = FK(User, SET_NULL, null=True)  # 课程组组长
teachers = M2M(User)                      # 本课程教师池
clazzes  = M2M(Clazz)                     # 本课程×学院下的班级
unique_together = (course, college)       # 同一课程×学院仅一条
```

**为什么要有这张表？** 课程和学院之间不只是"开没开设"，还带着三个属性：组长是谁、教师池有谁、有哪些班级。纯多对多存不了属性，所以用 `through` 显式建中间表，把属性挂在关系本身上——"带属性的多对多"。

`on_delete` 策略即业务规则：

| 删除对象 | 策略 | 意图 |
|---|---|---|
| 删课程/学院 | CASCADE | 关联记录无意义，一起删 |
| 删组长账号 | SET_NULL | 关联记录保留，组长置空（换人再指定） |
| 删学院（有班级） | PROTECT | 拒绝删除，保护历史数据 |

### 3.3 实际落库表清单

```
业务表（5）     users_user · academics_college · academics_clazz
                academics_course · academics_courscollege
M2M 中间表（4） academics_clazz_students · academics_clazz_teachers
                academics_courscollege_teachers · academics_courscollege_clazzes
权限表（5）     auth_group · auth_permission · auth_group_permissions
                auth_user_groups · django_content_type
系统表         django_session · django_migrations · axes_*（登录锁定记录）
```

M2M 在数据库里就是一张只含两个外键的中间表，Django 自动建表自动查。

### 3.4 设计要点

1. **四角色一张表**，角色 = Group，可多组共存
2. **班级是教学数据的容器**，教师/学生都挂在班级上 → 对象级校验的锚点
3. **课程×学院用带属性的中间表**，承载组长/教师池/班级三层信息
4. **on_delete 即业务规则**：PROTECT 防误删、SET_NULL 保关联、CASCADE 随主删
5. **待建**：teaching/models.py 的作业/提交/通知/资料/题库——将全部外键到 Clazz（班级）上，沿用"班级为容器"的思路

## 四、权限体系

```
权限体系（users 应用，已全部落地）
├── 注册：User.Meta.permissions —— 23 个权限点（admin 后台可见可勾选）
├── 映射：PERM_CODES —— 权限码 → codename
├── 分配：GROUP_PERMISSIONS + 数据迁移 0001~0009
│     ├── 教务   admin        5 项（class/course/user:*）
│     ├── 课程组 course_team   4 项（knowledge / material / question_bank / chapter）
│     ├── 教师   teacher       9 项（notice / analysis / material / homework×5）
│     └── 学生   student       4 项（homework:view · notice:view · material:view · analysis:view_self）
│           └─ 通用 profile:edit（四组都有）
├── 工具
│     ├── 功能级：hasPerm · getGroupKey
│     ├── 页面：requirePerm · requireTeacherGroup · requireStudentGroup
│     ├── API：PermRequired · IsTeacherGroup
│     └── 对象级：getTeacherClazz（执教班级）· getStudentClazz（所在班级）
└── 质量保障：checks.py 一致性检查 + tests.py 权限矩阵（11 用例）
```

## 五、请求校验流程（两级权限模型）

```
收到请求
  │
  ▼
① 登录了？ ───────否──────→ 页面 302 跳登录 / API 401
  │ 是
  ▼
② 分组入口校验（是不是教师组/学生组？）──否──→ 403
  │ 是
  ▼
③ 权限码校验 hasPerm（有没有这个功能？）──否──→ 403
  │ 是
  ▼
④ 对象级校验（这个班级我教/我在吗？）────否──→ 404（不暴露对象存在性）
  │ 是
  ▼
⑤ 执行业务逻辑
```

| 层级 | 载体 | 示例 |
|---|---|---|
| 功能级 | 分组权限码 | 教师有 `notice:manage` → 能用通知功能 |
| 对象级 | 业务接口内校验 | `clazz.teachers` 含当前教师 → 能对这个班发通知 |

①② = 页面装饰器；②③ = API 权限类；④ = getTeacherClazz / getStudentClazz。
第 ④ 层是防越权的关键：只查"能不能用"不够，还要查"能不能对这个对象用"。404 而非 403 是刻意设计：不暴露对象是否存在。

## 八、安全机制

1. **服务端强制校验**：前端隐藏菜单只影响体验，后端才是防线（页面装饰器 + API 权限类双轨）
2. **对象级校验**：教师→执教班级、学生→所在班级、教务→课程×学院上下文，越界一律 404
3. **防暴力破解**：django-axes 连续失败 5 次锁定 1 小时
4. **登出仅 POST**：防 CSRF 强制登出
5. **权限一致性检查**（users/checks.py）+ **权限测试矩阵**（users/tests.py），改权限必跑

## 九、业务规则

- 教师权限边界 = 其执教班级集合（含个人题库）；学生权限边界 = 自己所在班级
- 无法删除已截止作业（待作业模型落地时实现）
- 教务账号仅管理员在 /admin/ 添加；教师/学生 xlsx 导入自动入组
- 课程组组长由教务设置，自动入组/移出
- 班级详情必须从课程×学院入口进入（跨课程 404）
