## 一、背景：为什么需要教学班级

教务导入的**行政班（Clazz）**是学籍概念：学生按学号解析进班，一人一行政班。

但实际授课的组织单位是**教学班**：同一门课可能把两三个行政班合并成一个大班上课（合班），也可能一个行政班单独开课。教师发通知、布置作业、下发资料，针对的是"这批一起上课的学生"——即教学班。

**概念区分：**

| 概念 | 性质 | 决定方式 | 谁挂在上面 |
|---|---|---|---|
| 行政班 AdminClass（决策期称 Clazz） | 学籍单位 | 学号解析（学生一人一行政班） | 学生（经 ClassMembership 成员关系） |
| 教学班 TeachingClass | 授课单位 | 教务按学期组建（1~N 个行政班） | 教师、通知、作业、资料 |

## 二、决策记录（2026-10-18 定稿）

| 决策点 | 结论 | 理由 |
|---|---|---|
| 教学班能否跨学院合班 | **不可** | 教学班挂 CourseCollege（课程×学院）下，外键天然锁定一个学院 |
| 一个学生一门课进几个教学班 | **每学期一个** | 学生不直接挂教学班，由所在行政班推导——结构上天然满足，无需同步 |
| 表结构选型 | **保留 Clazz（落地后更名 AdminClass）+ 新增 TeachingClass** | 行政班是学籍事实不动，教务端零改动；教学班纯新增表 |

> 学期维度：教学班**按学期开设**（同一门课不同学期有不同教学班），表带 `term` 字段。

## 三、表结构设计

### 3.1 TeachingClass 模型

```python
class TeachingClass(models.Model):
    """教学班：授课单位，由 1~N 个行政班按学期组成（行政班是原子单位，不拆分）"""
    name = CharField(50)      # 教学班名（如"计科2301-2302合班"）
    term = CharField(20)      # 学期（如"2026-2027-1"，格式定稿后统一）
    courseCollege = FK(CourseCollege, PROTECT, related_name='teachingClasses')
    adminClasses = M2M(AdminClass, related_name='teachingClasses')  # 组成的行政班（1~N 个）
    teachers = M2M(User, related_name='teachingClasses')   # 授课教师
    # unique_together = (courseCollege, term, name)  # 同课程同学期班名唯一
```

### 3.2 ER 关系（在现有三层结构上新增一层）

```
users_user（平台账号）
   │
   ├─ teachers（授课教师）─────┐
   │                          │
   │  academics_adminclass（行政班）◄─┐
   │      │ major                    │ adminClasses（教学班的组成）
   │      ▼                          │
   │  academics_major（专业）          │
   │      │ department               │
   │      ▼                          │
   │  academics_department（学院）     │
   │      ▲                          │
   │      │ department               │
   │  academics_coursecollege（课程×学院）
   │      │ courseCollege（PROTECT）
   │      ▼
   │  academics_teachingclass（教学班）
   │      ├─ adminClasses（组成行政班 1~N）
   │      └─ teachers（授课教师）
   │              │
   └──────────────┘

实线 = ForeignKey；虚线 = ManyToMany（Django 自动建中间表）
```

### 3.3 学生归属的推导（本设计的核心）

**学生不直接挂教学班**，归属关系是推导出来的：

```
学生 → ClassMembership（当前在班：left_at IS NULL）
     → 行政班（学籍事实）
     → 行政班属于哪些教学班（adminClasses M2M）
     → 该学生本学期修这门课的教学班
```

为什么这样设计：
- 行政班是教学班的**原子组成单位**（不拆分行政班），所以"教学班 = 若干行政班的并集"自动成立
- 学生→教学班的映射由行政班事实推导，**不存在两张表需要同步的一致性问题**
- "一门课一学期只进一个教学班"由三条规则叠加天然保证：① 一个学生同一时间只有一个当前行政班（memberships 服务层约束）；② 一个行政班在同课程同学期只属于一个教学班（服务层约束 C2）；③ 行政班不可拆分组班

## 四、对象级校验路径（对权限体系的影响）

教学班已落地（2026-10-18），教师/学生业务接口的对象级校验锚点为 TeachingClass：

```
教师：teachingClass.teachers 含当前用户 → 否则 404（一跳）
学生：teachingClass.adminClasses 的 memberships（当前在班）含当前用户的学生资料 → 否则 404（三跳：学生→成员关系→行政班→教学班）
教务：管理入口仍走 课程→学院→教学班 上下文（与现有"必须从课程×学院进入"规则一致）
```

对应 helpers（已在 teaching/helpers.py 实现，测试矩阵覆盖）：

```python
getTeacherTeachingClass(user, teachingClassId)   # 授课教师校验
getStudentTeachingClass(user, teachingClassId)   # 学生经行政班推导校验
```

沿用现有设计：越界一律 **404**（防探测）、超级用户放行、失败快速。

## 五、服务层约束（写入接口时校验）

M2M 关系无法用数据库唯一约束表达，以下约束全部在**教学班管理接口**中服务端校验：

| 编号 | 约束 | 说明 |
|---|---|---|
| C1 | 组成行政班必须同学院 | 教学班所有行政班经 `major → department` 推导的学院必须等于 `courseCollege.department`，防跨学院合班 |
| C2 | 行政班不重复组班 | 一个行政班在同课程同学期只属于一个教学班（防同一批学生进两个班） |
| C3 | 教师必须来自教师池 | 教学班教师必须是该课程×学院教师池成员 |
| C4 | 班名唯一 | 同课程同学期教学班名唯一（unique_together） |
| C5 | 删除保护 | `on_delete=PROTECT`：有教学班的课程×学院删不掉 |

## 八、边界场景

| 场景 | 处理 |
|---|---|
| 重修生（跨学期再修同一门课） | 学生仍在原行政班，新学期的教学班按学期区分——学生通过新学期的教学班获得课程内容，互不干扰 |
| 转班（行政班变更） | memberships 表旧记录写 left_at、新记录起 joined_at（转班历史留痕），教学班归属自动迁移（推导式设计的红利），无需手工改教学班 |
| 一个行政班不同课程进不同教学班 | 自然支持：同一行政班可出现在多个课程×学院的多个教学班（C2 只限同课程同学期） |
| 拆班授课（行政班拆进多个教学班） | **不支持**（行政班是原子单位）；确需拆班时教务先拆行政班再组教学班 |
