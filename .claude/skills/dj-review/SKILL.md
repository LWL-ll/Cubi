# dj-review - Django 代码审查

## 用法

把你写的代码贴给我，说"用 dj-review 审查一下"，我会从以下几个维度帮你检查。

## 审查维度

### 1. 代码规范 (Style)

| 检查项 | 说明 | 严重程度 |
|--------|------|----------|
| PEP8 规范 | 缩进、命名、行宽、空行等 | Low |
| 命名规范 | 类名大驼峰、函数/变量蛇形、常量全大写 | Low |
| 导入规范 | 标准库→第三方→本地，分组排序 | Low |
| 类型提示 | 函数参数和返回值是否有 type hint | Medium |
| Docstring | 类、函数、模块是否有文档字符串 | Low |
| 注释质量 | 注释是否清晰、不过度、不误导 | Low |

### 2. Django 最佳实践 (Best Practice)

| 检查项 | 说明 | 严重程度 |
|--------|------|----------|
| 胖模型瘦视图 | 业务逻辑是否放在 Model/Service 而非 View | Medium |
| ORM 使用 | 是否正确使用 ORM，有没有滥用 raw SQL | Medium |
| 批量赋值防护 | 表单/序列化器是否显式指定 fields | High |
| 事务使用 | 多步数据库操作是否用事务包裹 | Medium |
| 异常处理 | 异常捕获是否合理，不裸 except | Medium |
| 信号滥用 | 是否过度使用信号导致逻辑分散 | Medium |
| Manager 使用 | 复杂查询是否封装到 Manager 中 | Low |
| URL 命名 | 是否使用命名 URL 而非硬编码路径 | Low |

### 3. 性能问题 (Performance)

| 检查项 | 说明 | 严重程度 |
|--------|------|----------|
| N+1 查询 | 循环中查询数据库 | High |
| 未使用 select_related / prefetch_related | 关联数据查询未优化 | High |
| 全表扫描 | 缺少索引的过滤/排序 | High |
| 查询集未切片 | 可能返回大量数据 | Medium |
| 序列化器 N+1 | 嵌套序列化器导致额外查询 | High |
| 内存泄漏 | 大查询集用 iterator() | Medium |
| 冗余查询 | 相同查询重复执行 | Medium |
| 文件操作 | 大文件是否流式处理 | Medium |

### 4. 可维护性 (Maintainability)

| 检查项 | 说明 | 严重程度 |
|--------|------|----------|
| 函数长度 | 函数是否超过 50 行 | Medium |
| 类的职责 | 类是否职责单一 | Medium |
| 重复代码 | 是否有重复的逻辑块 | Medium |
| 圈复杂度 | 条件分支是否过多 | Medium |
| 魔法数字 | 是否有未命名的数字常量 | Low |
| 深层嵌套 | 嵌套层级是否过深（超过3层） | Medium |
| 耦合度 | 模块间是否过度依赖 | Medium |
| 函数参数 | 参数是否过多（超过5个） | Low |

### 5. 测试质量 (Testing)

| 检查项 | 说明 | 严重程度 |
|--------|------|----------|
| 测试覆盖 | 新增代码是否有对应测试 | Medium |
| 边界条件 | 是否测试了边界情况 | Medium |
| 异常路径 | 是否测试了异常和错误场景 | Medium |
| 测试隔离 | 测试之间是否互相独立 | Low |
| Fixture 使用 | 是否合理使用 fixture | Low |

### 6. API 设计 (API Design) - DRF 项目

| 检查项 | 说明 | 严重程度 |
|--------|------|----------|
| RESTful 规范 | URL 命名、HTTP 方法使用是否规范 | Medium |
| 状态码使用 | 是否使用正确的 HTTP 状态码 | Medium |
| 统一响应格式 | 响应结构是否一致 | Low |
| 序列化器分层 | List/Detail/Create 是否区分 | Medium |
| 权限控制 | 每个接口是否明确了权限 | High |
| 分页 | 列表接口是否分页 | Medium |
| 过滤/搜索/排序 | 是否支持且安全 | Medium |
| 参数校验 | 输入验证是否完整 | High |

## 严重程度定义

- **Critical** — 必须立即修复，可能导致严重 bug 或安全问题
- **High** — 强烈建议修复，影响较大
- **Medium** — 建议修复，提升代码质量
- **Low** — 可选优化，风格/规范类

## Django 常见反模式清单

### Model 层反模式

1. **Fat Views** — 业务逻辑都写在视图里
   - 应该把业务逻辑放到 Model 方法或 Service 层

2. **过度使用信号 (Signals)** — 用信号串起复杂业务流程
   - 信号让代码流程难以追踪，优先用显式调用

3. **模型方法太多** — 一个模型几十个方法
   - 考虑用 Mixin 或 Service 层拆分

4. **在 __init__ 中做数据库查询**
   - 会导致每次实例化都查询，性能灾难

### View 层反模式

1. **函数视图太长** — 一个视图几百行
   - 拆分辅助函数，用类视图公用逻辑

2. **在视图里写复杂 SQL**
   - 应该封装到 Model Manager 中

3. **重复的权限检查代码**
   - 抽成装饰器或权限类

4. **手动解析请求参数**
   - 用表单或序列化器做验证

### Serializer 反模式

1. **一个 Serializer 走天下** — 列表/详情/创建/更新都用同一个
   - 应该分层设计，不同场景用不同 Serializer

2. **SerializerMethodField 滥用** — 每个字段都用方法字段
   - 优先用序列化器嵌套，注意 N+1

3. **在 Serializer 中写业务逻辑**
   - 序列化器只管数据转换，业务逻辑放 Service/Model

### QuerySet 反模式

1. **循环中查询** — 典型 N+1
   - 用 `select_related` / `prefetch_related`

2. **`.all()` 然后 Python 过滤**
   - 应该用 ORM 的 `filter()` 数据库层面过滤

3. **`len(queryset)` 代替 `.count()`**
   - 前者加载所有数据，后者只查 COUNT

4. **`if queryset:` 代替 `.exists()`**
   - 同样的问题，会加载所有数据

## 代码审查检查清单

每次审查按这个顺序走一遍：

- [ ] 代码能看懂吗？命名清晰吗？
- [ ] 有没有明显的 bug？
- [ ] 边界情况考虑了吗？（空值、零、最大、异常）
- [ ] 错误处理合理吗？
- [ ] 有没有性能问题？（N+1、大查询）
- [ ] 权限检查到位了吗？
- [ ] 输入验证了吗？
- [ ] 有没有重复代码可以抽？
- [ ] 注释够吗？会不会太多？
- [ ] 符合 Django 的惯用写法吗？
- [ ] 有对应的测试吗？
