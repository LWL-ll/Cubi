# dj-api-review - API 设计审查

## 用法

把你的 API 设计（接口列表、Serializer、ViewSet、URL 配置都行）贴给我，说"用 dj-api-review 审查一下"，我从多个维度帮你检查 API 设计的合理性。

---

## 审查维度

### 严重程度

| 等级 | 说明 |
|------|------|
| 🔴 严重 | 设计缺陷会导致安全问题或重大返工 |
| 🟠 高 | 不符合规范，影响联调或扩展性 |
| 🟡 中 | 体验不好或有更好的方案 |
| 💡 建议 | 最佳实践建议 |

## 一、RESTful 规范审查

### 1.1 URL 命名规范

| 检查项 | 正确示例 | 错误示例 | 严重程度 |
|--------|----------|----------|----------|
| 使用名词，不用动词 | `/api/books/` | `/api/getBooks/` | 🟡 |
| 复数形式 | `/api/users/` | `/api/user/` | 🟡 |
| 小写 + 连字符 | `/api/user-profiles/` | `/api/UserProfiles/` | 💡 |
| 层级关系清晰 | `/api/classes/{id}/students/` | `/api/students/?class_id=1` | 💡 |
| 不暴露内部结构 | `/api/orders/` | `/api/v1/order/endpoint/` | 💡 |

**常见问题：**

```
❌ 不好的 URL:
  /api/getUserList         → 动词
  /api/deleteOrder?id=123  → 动词 + 参数
  /api/userInfo            → 驼峰
  /api/v2_users            → 版本号位置错

✅ 好的 URL:
  GET    /api/users/           列表
  GET    /api/users/{id}/      详情
  POST   /api/users/           创建
  PUT    /api/users/{id}/      更新
  PATCH  /api/users/{id}/      部分更新
  DELETE /api/users/{id}/      删除
```

### 1.2 HTTP 方法使用

| 方法 | 用途 | 幂等 | 有请求体 |
|------|------|------|----------|
| GET | 获取资源 | ✅ | ❌ |
| POST | 创建资源 | ❌ | ✅ |
| PUT | 全量更新 | ✅ | ✅ |
| PATCH | 部分更新 | ❌ | ✅ |
| DELETE | 删除资源 | ✅ | ❌ |
| HEAD | 获取头部（同 GET 但无 body） | ✅ | ❌ |
| OPTIONS | 获取支持的方法 | ✅ | ❌ |

**常见问题：**
- 用 GET 做修改操作（严重，会被缓存、爬虫可能触发）
- 用 POST 做所有操作（不规范）
- DELETE 带请求体（不推荐，部分服务器会忽略）

## 二、响应格式审查

### 2.1 统一响应结构

**推荐的统一格式：**
```json
{
  "code": 0,
  "message": "success",
  "data": { ... }
}
```

**列表接口标准格式：**
```json
{
  "code": 0,
  "message": "success",
  "data": {
    "count": 100,
    "next": "https://api.example.com/users/?page=2",
    "previous": null,
    "results": [ ... ]
  }
}
```

**检查要点：**
- [ ] 成功和失败的响应结构是否一致
- [ ] 是否有统一的错误码
- [ ] 列表接口是否返回总数
- [ ] 分页信息是否完整（上一页/下一页/总数/当前页）
- [ ] 字段命名是否一致（驼峰 vs 下划线，前后端统一）

### 2.2 HTTP 状态码使用

| 场景 | 推荐状态码 | 常见错误 |
|------|-----------|----------|
| 查询成功 | 200 OK | 全部返回 200 |
| 创建成功 | 201 Created | 返回 200 |
| 删除成功 | 204 No Content | 返回 200 + null |
| 参数错误 | 400 Bad Request | 返回 200 + 错误码 |
| 未认证 | 401 Unauthorized | 返回 200 + 错误码 |
| 无权限 | 403 Forbidden | 返回 200 + 错误码 |
| 资源不存在 | 404 Not Found | 返回 200 + 空数据 |
| 资源冲突 | 409 Conflict | 返回 200 + 错误码 |
| 限流了 | 429 Too Many Requests | 返回 200 + 错误码 |
| 服务器错误 | 500 Internal Server Error | 返回 200 + 错误码 |

**常见问题：**
- 全部返回 200，用 code 字段区分（不推荐用 HTTP 状态码吗？其实两者结合最好）
- 401 和 403 分不清（未认证 vs 已认证但没权限）

## 三、错误处理审查

### 3.1 错误响应格式

**推荐格式：**
```json
{
  "code": 40001,
  "message": "参数验证失败",
  "errors": {
    "email": ["邮箱格式不正确"],
    "password": ["密码长度至少12位"]
  }
}
```

**检查要点：**
- [ ] 错误码是否有统一规划（按模块分段）
- [ ] 字段级错误是否有明确的字段名
- [ ] 错误消息是否对前端友好（不是堆栈信息）
- [ ] 是否包含足够的信息让前端展示错误
- [ ] 敏感信息是否从错误消息中移除

### 3.2 异常处理

- [ ] 是否有全局异常处理器
- [ ] 验证错误是否统一处理
- [ ] 权限错误是否统一返回
- [ ] 404 是否有统一格式
- [ ] 500 错误是否不泄露堆栈信息

## 四、分页、过滤、搜索、排序审查

### 4.1 分页

**检查清单：**
- [ ] 列表接口是否都支持分页
- [ ] 分页参数命名是否一致（page / page_size 或 offset / limit）
- [ ] 是否有最大分页限制（防止一次查太多）
- [ ] 是否返回总数 count
- [ ] 是否有下一页/上一页链接（或总页数）
- [ ] 大数据量是否考虑游标分页（避免 offset 性能问题）

### 4.2 过滤

**检查清单：**
- [ ] 常用过滤字段是否支持（状态、时间范围等）
- [ ] 过滤参数命名是否规范（`status`, `created_at__gte` 或 `startTime`）
- [ ] 是否支持多值过滤（`status__in=draft,published`）
- [ ] 是否有过滤字段白名单（防止 SQL 注入或无意义字段过滤）
- [ ] 外键过滤是传 ID 还是传名称（建议传 ID）

### 4.3 搜索

**检查清单：**
- [ ] 是否支持关键字搜索
- [ ] 搜索范围是否明确（哪些字段参与搜索）
- [ ] 大数据量搜索是否有性能问题（要不要用 Elasticsearch）
- [ ] 搜索结果是否高亮（可选）

### 4.4 排序

**检查清单：**
- [ ] 是否支持排序（`ordering` 参数）
- [ ] 支持的排序字段是否有白名单
- [ ] 默认排序是否明确（如 `-created_at`）
- [ ] 排序字段是否有索引

## 五、权限设计审查

| 检查项 | 严重程度 |
|--------|----------|
| 每个接口是否明确了权限要求 | 🔴 |
| 列表接口是否按权限过滤数据 | 🔴 |
| 详情接口是否有对象级权限检查 | 🔴 |
| 创建/更新/删除是否有权限检查 | 🔴 |
| 管理员接口是否区分了管理员权限 | 🟠 |
| 不同角色看到的字段是否有区分 | 🟡 |
| 批量操作是否有权限检查 | 🔴 |

详见 **dj-permcheck** 权限审查技能。

## 六、性能审查

### 6.1 列表接口性能

| 检查项 | 严重程度 |
|--------|----------|
| 列表接口是否有 N+1 问题 | 🔴 |
| 是否用了精简的列表序列化器 | 🟡 |
| 大字段（content/description）列表页是否不返回 | 🟡 |
| 列表查询是否有索引 | 🟠 |
| 深分页（page=1000+）是否有性能问题 | 🟡 |

### 6.2 写入接口性能

| 检查项 | 严重程度 |
|--------|----------|
| 创建/更新是否有不必要的查询 | 🟡 |
| 多步操作是否用了事务 | 🟠 |
| 批量操作是否用了 bulk_create / bulk_update | 🟡 |

## 七、版本管理审查

**检查清单：**
- [ ] 是否有 API 版本规划（v1, v2）
- [ ] 版本号在 URL 还是 Header 里（推荐 URL 里，更直观）
- [ ] 废弃接口是否标记 deprecated
- [ ] 破坏性变更是否走新版本
- [ ] 版本兼容性策略是否明确

**版本号位置对比：**

| 方案 | 示例 | 优点 | 缺点 |
|------|------|------|------|
| URL 版本 | `/api/v1/users/` | 直观、调试方便 | URL 不那么"干净" |
| Header 版本 | `Accept: application/vnd.api.v1+json` | URL 干净 | 不直观、调试麻烦 |
| 查询参数 | `/api/users/?version=v1` | 简单 | 不规范 |

## 八、接口一致性审查

### 8.1 命名一致性

- [ ] 所有列表用复数还是单数？（推荐复数）
- [ ] 字段命名是 snake_case 还是 camelCase？（前后端统一）
- [ ] 时间字段命名是否统一（`created_at` vs `createTime`）
- [ ] ID 字段名是否统一（`id` 还是 `userId` 之类）
- [ ] 状态值命名是否统一（`status`, `state`, `type`）

### 8.2 行为一致性

- [ ] 所有创建成功都返回 201 吗？
- [ ] 所有删除成功都返回 204 吗？
- [ ] 所有列表接口都有分页吗？
- [ ] 所有列表接口都支持过滤/搜索/排序吗？
- [ ] 错误码是否统一规划？

### 8.3 数据格式一致性

- [ ] 时间格式是否统一（ISO 8601: `2024-01-15T10:30:00Z`）
- [ ] 布尔值是否都是 true/false（不是 0/1 或 "true"/"false"）
- [ ] 空值用 null 还是空字符串/空数组
- [ ] 枚举值用字符串还是数字（推荐字符串，可读性好）

## 九、文档友好性审查

### 9.1 自动生成文档

- [ ] 是否集成了 drf-spectacular 或 drf-yasg
- [ ] 每个接口是否有描述
- [ ] 字段是否有 help_text / label
- [ ] 请求/响应示例是否完整
- [ ] 错误码是否有文档

### 9.2 前后端联调友好度

- [ ] 接口是否有清晰的分类（按模块分组）
- [ ] 创建/更新接口返回的数据结构是否和详情一致
- [ ] 枚举值是否有明确的选项说明
- [ ] 是否有 Mock 数据供前端联调
- [ ] 接口变更是否有通知机制

## 十、常见设计反模式

### ❌ 反模式 1: 万能接口

```
POST /api/action/
{ "action": "create_user", "data": {...} }
```

问题：一个接口干所有事，权限、缓存、文档都不好做。
正确：每个资源有独立的 RESTful 接口。

### ❌ 反模式 2: GET 做修改

```
GET /api/deleteUser/?id=123
```

问题：GET 应该是幂等、安全的，会被缓存、爬虫可能触发。
正确：用 DELETE 方法。

### ❌ 反模式 3: 过度嵌套

```
/api/schools/1/grades/2/classes/3/students/4/exams/5
```

问题：URL 太长，层级太深，前端拼起来麻烦。
正确：2-3 层就够了，深层的用独立接口 + 参数过滤。

### ❌ 反模式 4: 一个大接口返回所有数据

```
GET /api/home/ → 返回用户信息、通知、课程、作业、考试...
```

问题：数据量太大，不需要的也返回了，性能差。
正确：拆成多个接口，前端按需加载。

### ❌ 反模式 5: 状态码全是 200

```json
{ "code": 404, "message": "not found", "data": null }
```

问题：HTTP 状态码形同虚设，缓存、监控、网关都识别不了。
正确：HTTP 状态码 + 业务错误码结合使用。
