# dj-changelog - 变更日志生成

## 用法

把你这次修改的代码或变更描述给我，说"用 dj-changelog 生成"，我帮你整理成规范的变更日志。

---

## 变更类型

| 类型 | 标签 | 说明 | 版本号影响 |
|------|------|------|-----------|
| 新功能 | ✨ Feature | 新增功能、新增接口 | Minor 版本 +1 |
| Bug 修复 | 🐛 Fix | 修复 bug、修复问题 | Patch 版本 +1 |
| 重构 | 🔨 Refactor | 代码重构，不影响功能 | Patch 版本 +1 |
| 性能优化 | ⚡ Performance | 性能改进 | Patch 版本 +1 |
| 文档 | 📝 Docs | 文档、注释更新 | 不影响版本 |
| 测试 | ✅ Test | 测试代码变更 | 不影响版本 |
| 样式 | 💄 Style | 代码格式、命名调整 | 不影响版本 |
| 构建 | 🏗️ Build | 构建系统、依赖变更 | 视情况 |
| CI/CD | 🚀 CI | 持续集成配置变更 | 不影响版本 |
| 安全修复 | 🔒 Security | 安全相关修复 | Patch 或 Minor |
| 破坏性变更 | 💥 BREAKING | 不兼容的 API 变更 | Major 版本 +1 |

## 变更分类指南

### 怎么判断变更类型？

| 场景 | 类型 |
|------|------|
| 新增了一个 API 接口 | Feature |
| 新增了一个页面 | Feature |
| 新增了一个工具函数 | Feature / Refactor |
| 修复了某个 bug | Fix |
| 修复了安全漏洞 | Security |
| 代码重构，功能不变 | Refactor |
| 优化了查询性能 | Performance |
| 改了字段名，老 API 不能用了 | BREAKING |
| 加了注释、更新了 README | Docs |
| 加了测试用例 | Test |
| 改了代码格式、import 排序 | Style |
| 升级了依赖包 | Build |
| 修改了 CI 配置 | CI |

### 破坏性变更（BREAKING）怎么判断？

是破坏性变更如果：
- API 字段名改了，老前端调用会报错
- 接口 URL 变了
- 字段类型变了
- 删除了旧的接口
- 数据库表结构不兼容，需要数据迁移
- 权限结构变了，现有配置失效

## 数据库迁移变更记录

每次有 migration 时，单独记录：

```
【数据库变更】
- 新增迁移: 0012_add_role_table.py
  - 新增表: role, user_role, role_permission
  - 新增字段: user.role_id (外键)
  - 索引: role.name, user_role.user_id

- 迁移注意事项:
  - 迁移前请备份数据库
  - 迁移预计执行时间: < 10 秒
  - 迁移后需要执行初始化脚本填充角色数据
```

## API 变更记录

API 有变更时单独记录：

```
【API 变更】
新增接口:
- POST /api/v1/roles/ 创建角色
- GET  /api/v1/roles/ 角色列表
- PUT  /api/v1/roles/{id}/ 更新角色
- DELETE /api/v1/roles/{id}/ 删除角色

修改接口:
- GET /api/v1/users/ 增加角色过滤参数 role_id
  - 新增请求参数: role_id (可选)
  - 响应新增字段: role_name, role_id

废弃接口:
- GET /api/v1/groups/ (将在 2.0 移除，请用 /roles/ 替代)

破坏性变更:
- 无
```

## 语义化版本号 (SemVer)

```
MAJOR.MINOR.PATCH
  │     │     │
  │     │     └─ 修复 bug，向下兼容
  │     └─────── 新增功能，向下兼容
  └───────────── 破坏性变更，不兼容
```

**版本号递增规则：**

| 变更类型 | 版本变化 | 示例 |
|----------|----------|------|
| Bug 修复 | PATCH +1 | 1.2.3 → 1.2.4 |
| 新功能 | MINOR +1, PATCH 归零 | 1.2.3 → 1.3.0 |
| 破坏性变更 | MAJOR +1, MINOR/PATCH 归零 | 1.2.3 → 2.0.0 |

**初始版本：**
- 0.x.x — 开发阶段，快速迭代
- 1.0.0 — 第一个正式发布版本

## 生成步骤

给我变更内容后，我会按以下步骤整理：

1. **分类** — 把每个变更分到对应的类型
2. **归纳** — 相似的变更合并，突出重点
3. **影响评估** — 评估影响范围和风险
4. **版本建议** — 根据变更类型建议版本号
5. **注意事项** — 迁移、配置变更等需要注意的点
6. **格式化** — 按标准格式输出

## 提供信息的方式

你可以这样给我信息：

**方式 1：直接描述**
```
用 dj-changelog 生成：
这次改了用户模块，加了角色管理功能，修了登录的一个bug，还重构了权限检查的代码
```

**方式 2：文件列表 + 描述**
```
用 dj-changelog 生成：
新增了 roles/models.py, roles/views.py
修改了 users/views.py, users/serializers.py
删除了 old_groups/ 目录
主要是做 RBAC 角色权限系统
```

**方式 3：贴 git diff 或 commit log**
```
用 dj-changelog 生成，这是 git log：
- feat: 新增角色管理功能
- fix: 修复登录失败次数不重置的问题
- refactor: 重构权限后端
```

信息越详细，整理出来的 changelog 越准确 🎯
